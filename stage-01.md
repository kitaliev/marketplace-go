# Этап 1 — скелет сервиса

Ветка: `stage/01-skeleton`, основная ветка репозитория — `master`. Устройство — плоское, один пакет (раздел «Устройство: пока плоское», решение 2026-10-13). Типы, имена функций и разбивку по файлам придумываешь сам — я проверю на ревью.

## Зачем этот этап

Это фундамент, на котором будут стоять все следующие этапы:
- репозиторий;
- автоматическая проверка (CI);
- HTTP-сервер;
- хранилище товаров в памяти;
- корректная остановка.

Конкурентности здесь пока немного: мьютекс рядом с данными, флаг готовности на `atomic`, сервер в горутине, остановка по сигналу. Остальное — в журнале экспериментов про горутины.

## Устройство: пока плоское

Решение 2026-10-13: структуру проекта (слои, пакеты, кто кого импортирует) разберём в модуле про структуру сервиса, а на второй контрольной точке разнесём проект по выбранной схеме. До этого — минимум:

```
marketplace-go/
├── cmd/catalog/         весь сервис: один пакет main, разбитый по файлам по смыслу
│                        (запуск и остановка, хранилище, загрузка seed, обработчики, тесты рядом)
├── data/seed.json
├── experiments/, docs/experiments/
└── .github/workflows/ci.yml
```

Пакетов `internal/...` пока нет. Это не уменьшает требований к поведению: таблица ответов, мьютекс, остановка, тесты и CI — всё как ниже.

Два правила остаются и в плоском устройстве. Они не про раскладку, а про то, чтобы код можно было проверить тестом:
- **Ошибки возвращаются, процесс завершает только `main`.** `log.Fatal` и `os.Exit` есть только в `main`. Функция, которая сама завершает процесс, не проверяется тестом: тест упадёт вместе с ней. Удобный приём: `main` вызывает одну функцию, которая возвращает ошибку; все `defer` находятся в ней, а `main` пишет ошибку в лог и выходит с кодом 1.
- **Флаги разбирает только `main`** и передаёт значения дальше аргументами. Иначе тест не сможет передать свой путь к файлу, а повторный вызов упадёт с паникой «flag redefined».

## Что нужно знать про net/http для этого этапа

Модуль про HTTP будет позже, а для этапа хватит этого:
- **Обработчик — обычная функция.** `net/http` обслуживает каждое соединение в своей горутине, поэтому обработчики выполняются одновременно. Общие переменные, в которые обработчики пишут, — это гонка.
- **Порядок ответа:** заголовки (`w.Header().Set`), затем код (`w.WriteHeader`), затем тело (`w.Write` или JSON-кодировщик). При первой записи тела код и заголовки уходят клиенту, и поменять их уже нельзя. Если код не задан, при первой записи уйдёт `200`.
- **Запись ответа не завершает функцию.** После ответа с ошибкой нужен `return`.
- **`r.PathValue("id")`** — строка из шаблона; число из неё получают через `strconv.ParseInt`.
- **Тесты без порта:** `httptest.NewRequest` создаёт запрос, `httptest.NewRecorder` записывает ответ; обработчик (или весь `ServeMux`) вызывается напрямую, потом проверяются код, заголовки и тело.
- **Запуск и остановка сервера:** `ListenAndServe` блокирует вызвавшую горутину, пока сервер работает. После `Shutdown` или `Close` он возвращает `http.ErrServerClosed`, и это не ошибка.

## 1. Товары и стартовые данные

**Товар** (2026-10-13: ты вернулся к категории и бренду строками — принято, для этого этапа так проще):

| Ключ в JSON | Описание | Правило |
|---|---|---|
| `id` | целое | > 0 |
| `sku` | артикул продавца, например `CM-001` | не пустой |
| `name` | название | не пустое |
| `category` | категория, строка | не пустая |
| `brand` | бренд, строка | может быть пустым |

- **ID — `int64`.** В PostgreSQL идентификаторы хранятся в `bigint`, а это знаковый тип. Кроме того, отрицательный ID в файле тогда ловит твоя проверка с понятным сообщением, а не декодер JSON со своим.
- Цены и остатков у товара нет: они придут из внешних сервисов на следующих этапах.

**Стартовые данные** — `data/seed.json`: объект с ключом `products` (как у тебя), товаров 5–10.

При запуске сервис загружает этот файл. Путь задаётся флагом `-seed`, по умолчанию `data/seed.json`. Сервис **не стартует** (пишет понятную ошибку в лог и выходит с кодом 1), если:
- файла нет или в нём не JSON;
- нарушено правило из таблицы;
- два товара с одинаковым ID.

В ошибке видно, какой товар и что с ним не так. Например: `product id=7: empty sku`.

## 2. Хранилище товаров в памяти

- Две операции: «получить товар по ID» и «сохранить товар» (новый или с заменой существующего с тем же ID). Сохраняет `main` при загрузке seed, получают обработчики.
- Интерфейс для хранилища пока не нужен. Он появится, когда будем разносить проект по слоям.
- Реализация в памяти **безопасна для одновременного использования** из многих горутин.
- Мьютекс лежит рядом с данными, которые защищает. Методы с указателем.
- «Нет такого товара» — отдельная ошибка, которую вызывающий проверяет через `errors.Is`.
- **Наружу отдаётся копия.** Если вызывающий изменит полученный товар, данные в хранилище не изменятся. Иначе кто-то сможет менять данные в обход мьютекса, а это гонка.

## 3. HTTP API

Программа `cmd/catalog`. Роутер — стандартный `http.ServeMux` с шаблонами Go 1.22+ (метод и `{id}` прямо в шаблоне, значение берётся через `r.PathValue`).

| Запрос | Ответ |
|---|---|
| `GET /healthz` | всегда `200`, тело `ok`, пока процесс жив |
| `GET /readyz` | `200`, тело `ready`, пока сервис принимает запросы; `503`, тело `shutting down`, как только началась остановка |
| `GET /products/{id}` | `200` и товар в JSON (те же ключи, что в seed) |
| — товара нет | `404`, тело `{"error":"product not found"}` |
| — `id` не целое > 0 (`abc`, `0`, `-5`, `1.5`) | `400`, тело `{"error":"invalid product id"}` |

- У JSON-ответов заголовок `Content-Type: application/json`.
- Другие методы на тех же путях (`POST /products/1`) — `405`. Стандартный роутер делает это сам, если в шаблоне указан метод. Проверь, что так и есть.

**Зачем два адреса проверки.** Kubernetes будет спрашивать `/healthz` («процесс жив? если нет — перезапущу») и `/readyz` («можно слать запросы? если нет — уберу из балансировки»). Во время остановки процесс жив, но запросы на него слать уже нельзя.

**Таймауты сервера** — обязательно. Без них один медленный клиент может держать соединение вечно, и это утечка горутин:
- `ReadHeaderTimeout` 5 с — сколько ждать заголовки запроса;
- `ReadTimeout` 10 с — весь запрос целиком;
- `WriteTimeout` 10 с — запись ответа;
- `IdleTimeout` 60 с — сколько держать открытым соединение без запросов.

## 4. Логи

`log/slog` с JSON-обработчиком в stdout (`slog.NewJSONHandler`). Минимум сообщений:
- «сервер запущен» с адресом;
- «получен сигнал остановки»;
- «сервер остановлен»;
- ошибки.

Логирование каждого запроса — не сейчас, это девятый этап.

## 5. Остановка

Флаги: `-addr` (по умолчанию `:8080`) и `-shutdown-timeout` (по умолчанию 10 с).

1. SIGINT или SIGTERM → флаг готовности переключается, и `/readyz` отвечает `503`. Флаг читают и пишут разные горутины, поэтому он атомарный.
2. `Shutdown` сервера с таймаутом остановки. Не успел — принудительное закрытие.
3. Выход: код 0, если всё остановилось чисто, иначе 1.

**Обязательно:**
- `main` не завершается, пока не вернулся `Shutdown`;
- `http.ErrServerClosed` от запуска сервера — не ошибка;
- никаких `log.Fatal` и `os.Exit` там, где должны выполниться `defer`.

Подробный порядок остановки с воркерами и снимком — на десятом этапе.

## 6. CI

Файл `.github/workflows/ci.yml` — GitHub Actions. Что это такое:
- **workflow** — сценарий, который GitHub запускает сам на своих машинах;
- **job** — набор шагов на одной машине;
- **step** — один шаг: либо готовое действие (`uses:`), либо команда (`run:`).

Запуск: при push в `master` и при каждом pull request. Один job на `ubuntu-latest`, шаги:
1. Получить код — действие `actions/checkout`.
2. Поставить Go — действие `actions/setup-go`, версию брать из `go.mod` (параметр `go-version-file`).
3. `go vet ./...`.
4. Линтер — действие `golangci/golangci-lint-action`, версия golangci-lint `v2.13.2` (у тебя локально та же).
5. `go test -race -count=1 ./...`.
6. `go build ./...`.

Как писать, смотри в документации: «Building and testing Go» на docs.github.com и README `golangci-lint-action`.

В README добавь значок статуса CI. Его адрес даёт сам GitHub на странице workflow: «⋯ → Create status badge».

## 8. Что покрыть тестами

Твои тесты, стиль на твоё усмотрение. Обязательно зелёные с `-race`.

1. **Хранилище:**
   - найти существующий;
   - не найти несуществующий (ошибка через `errors.Is`);
   - сохранить с заменой;
   - изменение полученной копии не меняет хранилище;
   - одновременные чтения и записи из 50+ горутин.
2. **Загрузка seed:**
   - нормальные данные;
   - битый JSON;
   - ID ≤ 0;
   - пустое обязательное поле;
   - дубль ID.
3. **HTTP** (через `net/http/httptest`, без настоящего порта):
   - `200` с правильным JSON и `Content-Type`;
   - `404`;
   - `400` на `abc`, `0`, `-5`;
   - `405` на `POST`.
4. **`/readyz`:** `200`, а после переключения флага — `503`.
5. **goleak** (`go.uber.org/goleak`) в пакете, где тесты запускают горутины.

## 9. Журнал экспериментов

- Программы экспериментов — в `experiments/NN-name/`, каждая своя `package main`.
- Отчёты — в `docs/experiments/NN-name.md`. Шаблон отчёта: Goal / Setup / How to run / Output (настоящий вывод) / Why (объяснение) / Takeaway (вывод одной-двумя фразами).
- Эксперимент, которому нужна другая версия Go в `go.mod`, — отдельный модуль в своей папке со своим `go.mod`. Тогда `./...` из корня его не трогает.

**01-goroutines** — горутины на практике:
1. **`main` не ждёт.**
   - Отдельная программа: поднимает HTTP-сервер в горутине и сразу выходит из `main`, не дожидаясь ничего. Запусти, попробуй `curl`, объясни, что произошло и почему.
   - Свяжи это с тем, как устроена остановка в твоём сервисе.
2. **Паника.**
   - Программа с HTTP-сервером и двумя адресами: обработчик первого паникует сам, обработчик второго запускает горутину, которая паникует.
   - Дёрни оба через `curl`. Что стало с сервером в каждом случае и почему по-разному? Подсказка к объяснению: `net/http` сам ставит `recover` вокруг обработчика, но только в своей горутине.
3. **Переменная цикла.**
   - Цикл запускает горутины, каждая печатает переменную цикла.
   - Запусти с `go 1.21` в `go.mod` этого эксперимента и с `go 1.22`. Покажи разницу.
4. **Порядок горутин.**
   - `GOMAXPROCS(1)`, пять горутин печатают свой номер. Запусти несколько раз. Объясни через G-M-P, почему порядок именно такой (где оказывается последняя запущенная горутина).
   - Запусти с `-race` и сравни.
5. **Цена горутин.**
   - Три волны по 100 000 горутин, каждая ждёт сигнала.
   - Замерь время запуска волны и память процесса (`runtime.MemStats`: `Sys`, `StackInuse`). Объясни, почему вторая и третья волны быстрее первой.
